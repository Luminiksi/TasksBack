# TaskFlow — Требования к MVP

**Статус:** Draft  
**Версия документа:** 1.0  
**Тип документа:** Software Requirements Specification (SRS)

## 1. Цель проекта

TaskFlow — веб-приложение для управления проектами и задачами с использованием Kanban-досок.

Цель MVP — реализовать базовую систему, в которой пользователь может создавать несколько проектов, управлять задачами внутри каждого проекта, распределять задачи по колонкам доски и отслеживать их приоритеты, сроки и исполнителей.

Проект разрабатывается в учебных целях и для формирования портфолио Java-разработчика.

## 2. Область действия

### 2.1. Входит в MVP

- Создание и просмотр нескольких проектов.
- Редактирование информации о проекте.
- Отдельная Kanban-доска для каждого проекта.
- Создание, просмотр, редактирование и мягкое удаление задач.
- Восстановление удалённых задач.
- Настройка колонок Kanban-доски.
- Перемещение задач между колонками.
- Приоритеты задач.
- Сроки выполнения.
- Необязательное назначение исполнителя.
- Поиск и фильтрация активных задач.
- Хранение данных в PostgreSQL.
- REST API на Spring Boot.
- Веб-интерфейс на HTML, CSS и JavaScript без frontend-фреймворков.
- Автоматические тесты основных сценариев и бизнес-правил.

### 2.2. Не входит в MVP

Следующие функции могут быть рассмотрены после реализации первой версии:

- Регистрация, вход и управление учётными записями.
- Ролевая модель доступа и разграничение прав.
- Совместная работа нескольких авторизованных пользователей.
- Комментарии к задачам.
- История изменений и аудит действий.
- Загрузка вложений.
- Уведомления.
- Спринты и планирование итераций.
- Диаграммы и расширенная аналитика.
- Интеграции со сторонними сервисами.
- Мобильное приложение.

Функции из этого списка не должны добавляться в MVP без отдельного согласования.

## 3. Термины и определения

| Термин | Определение |
|---|---|
| Проект | Контейнер для задач и собственной Kanban-доски |
| Задача | Единица работы с названием, описанием и дополнительными атрибутами |
| Kanban-доска | Представление задач проекта в виде колонок |
| Колонка | Этап или категория, в которой отображаются задачи |
| Приоритет | Относительная важность задачи |
| Исполнитель | Текстовое имя или обозначение ответственного за задачу |
| Мягкое удаление | Пометка записи как удалённой без физического удаления из базы данных |
| MVP | Минимальная версия продукта, реализующая основные пользовательские сценарии |

## 4. Роли и ограничения пользователей

В MVP отсутствуют регистрация и авторизация. Приложение не определяет индивидуальные права доступа пользователей.

Предполагается локальное или учебное использование приложения без разграничения доступа между пользователями.

Поле исполнителя в MVP хранится как необязательное текстовое значение. Оно не связано с учётной записью и не подразумевает наличие системы пользователей. После реализации авторизации модель исполнителей может быть пересмотрена.

## 5. Функциональные требования

### 5.1. Управление проектами

**FR-01. Создание проекта**

Система должна позволять создавать проект с обязательным названием и необязательным описанием.

**FR-02. Просмотр проектов**

Система должна отображать список доступных активных проектов.

**FR-03. Просмотр проекта**

Пользователь должен иметь возможность открыть проект и просмотреть его Kanban-доску.

**FR-04. Редактирование проекта**

Система должна позволять изменять название и описание проекта.

**FR-05. Изоляция данных проектов**

Каждая задача и каждая колонка должны принадлежать определённому проекту. Доска одного проекта не должна отображать задачи другого проекта.

Удаление проекта и восстановление удалённого проекта не входят в согласованный объём MVP и требуют отдельного определения правил.

### 5.2. Управление Kanban-доской

**FR-06. Создание доски**

При создании проекта система должна создавать связанную с ним Kanban-доску.

**FR-07. Настройка колонок**

Пользователь должен иметь возможность создавать, переименовывать и удалять колонки доски.

**FR-08. Порядок колонок**

Пользователь должен иметь возможность изменять порядок колонок. Система должна сохранять заданный порядок.

**FR-09. Удаление колонки**

Система не должна допускать потерю активных задач при удалении колонки. Если в колонке есть задачи, удаление должно быть отклонено с понятным сообщением либо пользователь должен предварительно переместить задачи в другую колонку.

**FR-10. Отображение задач**

Доска должна отображать активные задачи в колонках, которым они назначены.

**FR-11. Перемещение задач**

Пользователь должен иметь возможность перемещать задачу между колонками. После успешного перемещения новое положение должно сохраняться в базе данных.

### 5.3. Управление задачами

**FR-12. Создание задачи**

Пользователь должен иметь возможность создать задачу в выбранном проекте и колонке.

Задача должна поддерживать следующие поля:

| Поле | Обязательность | Описание |
|---|---|---|
| Название | Обязательно | Краткое название задачи |
| Описание | Необязательно | Подробности задачи |
| Приоритет | Необязательно | LOW, MEDIUM, HIGH или CRITICAL |
| Срок выполнения | Необязательно | Дата, к которой желательно завершить задачу |
| Исполнитель | Необязательно | Текстовое имя или обозначение ответственного |
| Колонка | Обязательно | Колонка доски, в которой находится задача |

Если пользователь не указал приоритет, система должна устанавливать значение MEDIUM.

**FR-13. Просмотр задачи**

Пользователь должен иметь возможность просмотреть все поля активной задачи.

**FR-14. Редактирование задачи**

Пользователь должен иметь возможность изменять название, описание, приоритет, срок выполнения и исполнителя задачи.

**FR-15. Мягкое удаление задачи**

При удалении задачи система должна помечать её как удалённую, не удаляя физически из базы данных.

Удалённая задача не должна отображаться на обычной Kanban-доске и в стандартных списках активных задач.

**FR-16. Просмотр удалённых задач**

Система должна предоставлять возможность просматривать удалённые задачи отдельно от активных.

**FR-17. Восстановление задачи**

Пользователь должен иметь возможность восстановить удалённую задачу. После восстановления задача должна снова отображаться среди активных задач в прежнем проекте и колонке, если проект и колонка доступны.

**FR-18. Поиск задач**

Пользователь должен иметь возможность искать активные задачи по названию.

**FR-19. Фильтрация задач**

Пользователь должен иметь возможность фильтровать активные задачи по приоритету, колонке и исполнителю.

## 6. Бизнес-правила

**BR-01. Обязательное название**

Название проекта и название задачи не могут быть пустыми или состоять только из пробельных символов.

**BR-02. Приоритет**

Допустимые значения приоритета:

- `LOW` — низкий.
- `MEDIUM` — средний.
- `HIGH` — высокий.
- `CRITICAL` — критический.

Система должна отклонять недопустимые значения.

**BR-03. Срок выполнения**

Срок выполнения хранится как календарная дата без времени. Отсутствие срока допустимо. Просроченная задача остаётся доступной для просмотра и редактирования.

**BR-04. Принадлежность задачи**

Задача должна ссылаться на существующий проект и колонку, принадлежащую доске этого проекта.

**BR-05. Удалённые задачи**

По умолчанию все операции просмотра активных задач, поиска и фильтрации должны исключать мягко удалённые задачи.

Операции просмотра удалённых задач и восстановления должны работать с ними явно.

**BR-06. Восстановление задачи**

Восстановленная задача должна сохранять свои поля и прежнюю принадлежность проекту и колонке, если эти сущности существуют и доступны.

**BR-07. Удаление колонки с задачами**

Нельзя удалять колонку, пока в ней находятся активные задачи. Пользователь должен сначала переместить их в другую колонку.

**BR-08. Настраиваемые колонки**

Колонки принадлежат конкретной доске. Их названия и порядок могут различаться между проектами.

**BR-09. Исполнитель**

Исполнитель необязателен. В MVP его значение хранится как текст, без проверки существования пользователя.

**BR-10. Согласованность данных**

Система должна предотвращать создание задач со ссылками на несуществующие проекты и колонки, а также перемещение задачи в колонку другого проекта.

## 7. Нефункциональные требования

### 7.1. Архитектура и технологии

**NFR-01. Backend**

Backend должен быть реализован на Java с использованием Spring Boot и предоставлять REST API.

**NFR-02. Frontend**

Frontend должен использовать HTML5, CSS3 и JavaScript ES Modules без React и других frontend-фреймворков.

**NFR-03. База данных**

PostgreSQL должна использоваться для постоянного хранения проектов, досок, колонок и задач.

**NFR-04. Взаимодействие компонентов**

Frontend должен взаимодействовать с backend через HTTP-запросы к REST API. Обмен данными должен выполняться в формате JSON, где это применимо.

**NFR-05. Миграции**

Изменения структуры базы данных должны управляться версионируемыми миграциями, например с использованием Flyway.

### 7.2. Надёжность и обработка ошибок

**NFR-06. Валидация**

Данные должны проверяться на backend независимо от клиентской валидации.

**NFR-07. Ошибки API**

API должен возвращать подходящие HTTP-статусы и понятное описание ошибки. Внутренние технические детали и stack trace не должны отправляться клиенту в обычных ответах об ошибках.

**NFR-08. Сохранение данных**

Успешно сохранённые данные должны оставаться доступными после перезапуска приложения при условии сохранности базы данных.

**NFR-09. Согласованность операций**

Изменения, требующие нескольких связанных операций с базой данных, должны выполняться транзакционно там, где это необходимо для сохранения целостности данных.

### 7.3. Удобство использования

**NFR-10. Понятный интерфейс**

Интерфейс должен предоставлять понятные действия для создания, редактирования, удаления и восстановления задач.

**NFR-11. Обратная связь**

Пользователь должен получать сообщение об успешном действии или об ошибке.

**NFR-12. Состояния интерфейса**

Интерфейс должен корректно отображать состояния загрузки, пустые списки и ошибки получения данных.

### 7.4. Поддерживаемость и тестирование

**NFR-13. Структура кода**

Код должен быть организован по логическим модулям и слоям ответственности.

**NFR-14. Автоматические тесты**

Критическая бизнес-логика должна покрываться автоматическими тестами.

**NFR-15. Документация API**

Основные REST endpoints, форматы запросов и ответов, а также типичные ошибки должны быть задокументированы.

**NFR-16. Безопасность**

Backend должен валидировать входные данные и использовать параметризованные механизмы доступа к базе данных через выбранные средства работы с данными. Даже без авторизации приложение не должно полагаться исключительно на клиентскую проверку данных.

Конкретные численные требования к производительности и максимальному количеству задач пока не задаются: они могут быть определены после появления рабочего прототипа.

## 8. Основные пользовательские сценарии

### UC-01. Создание проекта

**Предусловие:** приложение запущено.

1. Пользователь открывает список проектов.
2. Нажимает «Создать проект».
3. Вводит название и, при необходимости, описание.
4. Подтверждает создание.
5. Система проверяет данные и сохраняет проект.
6. Система создаёт доску проекта.
7. Новый проект появляется в списке.

**Альтернативный сценарий:** если название пустое, система показывает ошибку и не создаёт проект.

### UC-02. Создание задачи

**Предусловие:** существует проект с доской и хотя бы одной колонкой.

1. Пользователь открывает доску проекта.
2. Выбирает колонку и действие «Создать задачу».
3. Вводит название и при необходимости описание, приоритет, срок и исполнителя.
4. Подтверждает создание.
5. Система проверяет данные и сохраняет задачу.
6. Новая задача появляется в выбранной колонке.

**Альтернативный сценарий:** при некорректных данных система показывает ошибку, задача не создаётся.

### UC-03. Перемещение задачи

**Предусловие:** существует активная задача и целевая колонка в той же доске.

1. Пользователь перемещает задачу в другую колонку.
2. Frontend отправляет запрос на backend.
3. Backend проверяет существование задачи и целевой колонки.
4. Backend сохраняет новое положение.
5. Frontend отображает задачу в новой колонке.

**Альтернативный сценарий:** если целевая колонка не принадлежит доске задачи, операция отклоняется.

### UC-04. Мягкое удаление и восстановление задачи

**Предусловие:** существует активная задача.

1. Пользователь выбирает удаление задачи.
2. Система помечает задачу как удалённую.
3. Задача исчезает с активной доски.
4. Пользователь открывает список удалённых задач.
5. Выбирает задачу и выполняет восстановление.
6. Система снимает признак удаления.
7. Задача снова отображается на активной доске.

### UC-05. Настройка колонок

**Предусловие:** существует проект с доской.

1. Пользователь открывает настройки доски.
2. Создаёт новую колонку или изменяет название существующей.
3. При необходимости меняет порядок колонок.
4. Сохраняет изменения.
5. Система сохраняет настройки, а доска отображает обновлённую структуру.

Если пользователь пытается удалить колонку с активными задачами, система сообщает, что сначала необходимо переместить задачи.

### UC-06. Поиск и фильтрация

**Предусловие:** на доске есть активные задачи.

1. Пользователь вводит часть названия задачи или выбирает фильтры.
2. Система получает соответствующие активные задачи.
3. Интерфейс отображает результаты, соответствующие условиям поиска и фильтрации.

Если результатов нет, интерфейс отображает понятное пустое состояние.

## 9. Критерии приёмки MVP

MVP считается функционально готовым, если выполняются все следующие условия:

- [ ] Можно создать несколько проектов и открыть каждый из них отдельно.
- [ ] У каждого проекта есть собственная доска с настраиваемыми колонками.
- [ ] Можно создавать, просматривать и редактировать задачи.
- [ ] У задачи доступны название, описание, приоритет, срок и необязательный исполнитель.
- [ ] Некорректные данные отклоняются backend с понятным ответом.
- [ ] Задачи можно перемещать между колонками одной доски.
- [ ] Задачи можно мягко удалять, просматривать в списке удалённых и восстанавливать.
- [ ] Поиск и фильтрация не возвращают удалённые задачи.
- [ ] Данные сохраняются в PostgreSQL и доступны после перезапуска приложения.
- [ ] Frontend работает с backend через REST API.
- [ ] Основные сценарии покрыты автоматическими тестами.
- [ ] Основные REST endpoints и правила запуска приложения описаны в документации.

## 10. Предполагаемые API-операции

Этот раздел фиксирует функциональные потребности, но не является окончательной спецификацией API. Точные URL, форматы DTO и коды ответов будут определены в отдельном документе по REST API.

| Ресурс | Необходимые операции |
|---|---|
| Проекты | Создание, список, получение по ID, редактирование |
| Колонки доски | Создание, список, переименование, изменение порядка, удаление при допустимых условиях |
| Задачи | Создание, список, получение по ID, редактирование, перемещение |
| Удалённые задачи | Список удалённых задач, восстановление |
| Поиск и фильтрация | Получение активных задач с параметрами поиска и фильтров |

## 11. Допущения и открытые вопросы

Следующие решения необходимо уточнить при проектировании модели данных и API:

1. Максимальная длина названия и описания проекта и задачи.
2. Минимальное количество колонок на доске и возможность переименования или удаления всех колонок.
3. Нужно ли запрещать повторяющиеся названия колонок в пределах одной доски.
4. Какой формат отображения задач использовать: отдельная страница, модальное окно или боковая панель.
5. Нужны ли пагинация и сортировка списка задач в первой версии.
6. Нужно ли восстанавливать задачу, если её прежняя колонка была удалена.
7. Какой механизм ограничения доступа будет использоваться при развёртывании приложения вне локальной учебной среды.

Эти вопросы не должны блокировать начало разработки базовых функций, если для конкретной задачи можно принять временное решение и явно задокументировать его.
